## 0. 개발 AI 도구 · 프롬프트 · 활용 내역

### 0-1. 사용 도구

| 도구 | 버전/형태 | 활용 |
|------|-----------|------|
| Cursor Agent | IDE 에이전트 | 기획 문서, 벤치마크, 구현, 리팩터, 밸런스, 패키징 |
| Playwright | Node | `?demo=1` 자동 플레이 녹화 → 시연 webm |
| reportlab | Python | Markdown → 제출용 PDF |

외부 LLM API를 런타임에 호출하지 않습니다.  
인게임 Director는 **규칙 기반(state machine + budget + memory)** 이며, 개발 과정에서 AI 코딩 에이전트를 집중 활용했습니다.

### 0-2. 작업 루프 (Observe → Decide → Rebuild → Verify)

NAN식 프로세스와 동일하게, 사람+에이전트가 다음 루프를 반복했습니다.

| 단계 | 질문 | 산출물 |
|------|------|--------|
| Observe | 무엇을 베낄 것인가? | `STEAM_POPULAR_BENCHMARK.md`, `BENCHMARK_PLAN.md` |
| Decide | 무엇을 버릴 것인가? | 격자 데모 폐기, 탑다운+Director UI 확정 (`docs/design/core_loop.md`) |
| Rebuild | 무엇을 구현할 것인가? | `game.js` Phase/Memory/Why/MOD/보스/Q |
| Verify | 무엇이 깨졌는가? | `tools/playtest.mjs`, softlock/클리어 버그 수정 |

### 0-3. 대표 프롬프트 (실제 사용 패턴)

프롬프트는 “코드 한 줄 작성”보다 **설계 제약과 검증 기준**을 넣는 형태로 사용했습니다.

1. **벤치마크**  
   “스팀 인기 액션/로그라이크/RPG에서 ‘이식 가능한 재미’만 표로 추출하고, 7분 런에 안 들어가는 것은 제외해라.”

2. **장르 결정**  
   “격자 미로 데모는 연출 설득력이 약하다. NAN 심사자가 7분 안에 Director를 이해하게 만드는 장르로 재설계 플랜을 세워라.”

3. **Director 설득력**  
   “AI를 썼다는 말이 아니라, Why 패널에 개입 사유가 남아 ‘연출 시스템’임을 증명해라. PEAK_FADE에서는 spawn을 금지해라.”

4. **완성도**  
   “Safe는 안정, Elite는 위험하지만 숙련 시 클리어 가능하게. playtest로 Softlock·클리어 불가 버그를 잡고 문서를 갱신해라.”

5. **제출물**  
   “Google Form 기준(GitHub / YouTube / PDF)에 맞게 소개서·AI문서 분량을 심사 가능 수준으로 보강해라.”

### 0-4. AI 활용의 경계

| 한 것 | 하지 않은 것 |
|-------|--------------|
| 설계 초안·표·구현·테스트 자동화 | 런타임 생성형 적/대사 API |
| 벤치마크 요약 | 타 작품 에셋 복제 |
| Why 문장 템플릿 설계 | 블랙박스 “알아서 해줘” 연출 |

즉, AI는 **제작 가속 도구**이고, 게임 안의 지능은 **설명 가능한 규칙 엔진**입니다.  
이 이중 구조가 NAN(제작 AI + 인게임 AI) 주제에 맞다고 판단했습니다.

## 1. 인게임 AI Director — 문제 정의

액션 로그라이크에서 “랜덤 스폰”만 있으면 긴장감이 우연에 의존합니다.  
Director Loop의 Director는 다음을 목표로 합니다.

1. **Intensity**를 읽고 Peak를 만든다.  
2. Peak 이후 **반드시 호흡(PEAK_FADE)** 을 준다.  
3. 플레이어의 스타일·직전 방 결과를 **기억**해 개입한다.  
4. 개입마다 **Why**를 남겨 블랙박스가 되지 않게 한다.

---

## 2. 아키텍처: Observe → Decide → Act → Explain

```
[플레이 입력/상태]
    → Observe (intensity, style, memory, threat, mod)
    → Decide (phase 전이, action 후보, budget 검사)
    → Act (spawn / heal / suppress / banner)
    → Explain (Why UI, Timeline, Run Report)
```

| 단계 | 주요 입력 | 출력 |
|------|-----------|------|
| Observe | HP비, 최근 피격창, near-miss, 적 threat 합, Style 추정 | Intensity 목표치 |
| Decide | Phase, phaseT, budget, Memory 플래그, Room MOD | Action 또는 suppress |
| Act | spawn_pack, spawn_elite, drop_heal, phase change | 월드/UI 변경 |
| Explain | 사유 문자열 | Why / Memory / Trace / Report |

구현 파일: `game/game.js` (`updateDirector`, `intervene`, `setWhy`, `logIntervention`, `endRun`).

---

## 3. Phase 상태머신 (L4D 교훈)

| Phase | 진입 조건 | 허용 | 금지 | Why 예시 |
|-------|-----------|------|------|----------|
| BUILD | 런/방 시작, RELAX 종료 | top-up pack | — | `BUILD top-up · budget-12` |
| SUSTAIN_PEAK | intensity ≥ peakThreshold 또는 room intent | elite 개입 | — | `Style 지속 · Peak · Elite` |
| PEAK_FADE | sustain 최소시간 경과 | 전투만 | **spawn/elite 개입** | `PEAK_FADE · spawn 억제` |
| RELAX | fade 완료 또는 Safe | heal | 과도한 압박 | `RELAX · HP<75 · Heal` |

### 설계 포인트
- Peak만 있으면 “항상 어려운 게임”이 되고, Fade가 없으면 Director가 스팸처럼 보입니다.  
- 그래서 PEAK_FADE를 **하드 억제**로 구현했습니다. (soft-cap이 아니라 early-return)

## 4. Intensity · Style · Budget

### Intensity
대략 다음 가중합으로 목표 intensity를 만들고 부드럽게 추적합니다.

- 적 threat (보스/엘리트/탱크 가중)
- 저체력 비율
- 최근 피격 윈도우
- near-miss 누적

### Style (플레이 분류)
이동량·대시·킬레이트·피격률로 Aggressive / Cautious / Mobile을 추정합니다.  
스타일 전환 시 Memory와 Why가 갱신되며, 이후 스폰 구성(원거리/swarm/sniper 비중)에 영향을 줍니다.

### Budget
개입은 공짜가 아닙니다. budget을 소모하며, Pupil 세트·PRESSURE MOD는 회복 속도를 바꿉니다.  
→ Director가 “항상 최강 개입”을 하지 못하게 하는 경제입니다.

---

## 5. Memory → Action → Why

| Memory | 감지 | Action | Why 템플릿 |
|--------|------|--------|------------|
| No-Hit | 직전 방 피격 0 | Elite Pack | `Memory No-Hit · budget 28 · Elite Pack` |
| Heavy Damage | 직전 방 피격 ≥ 35 | Heal drop | `Memory 다수 피격 · budget 18 · Heal` |
| Style shift | 스타일 변경 | 대응 스폰 가중 | `Style → Mobile (플레이 패턴 재분류)` |
| Fork | Safe/Elite 선택 | 방 템플릿 변이 | `플레이어 고위험 선택 · Rare 확정 루트` |
| Room MOD | 방 입장 | 규칙 파라미터 | `Room mod FOG — 시야 제한 · 근거리 유리` |
| Stall | 장시간 무킬 | 적 약화(교착 해제) | `교착 감지 → 적 약화` |

Why는 단순 로그가 아니라 **결정 근거 문장**입니다.  
심사자/플레이어가 “지금 왜 엘리트가 나왔는지”를 패널에서 읽을 수 있습니다.

---

## 6. Room Modifier (규칙 카드)

| MOD | 파라미터 영향 | 연출 목적 |
|-----|----------------|-----------|
| HASTE | 적 이속 ↑ | BUILD 압박 |
| BRITTLE | 적 HP ↓, 피격 ↑ | 하이리스크 |
| RICH | XP ↑ | 성장 가속 |
| FOG | 시야 비네팅 | 포지셔닝 유도 |
| PRESSURE | budget 재생 ↑ | Peak/Boss 가속 |

MOD는 콘텐츠 양이 아니라 **동일 맵에서 규칙이 바뀌는 디렉팅**을 싸게 만드는 장치입니다.

---

## 7. 플레이어 의사결정과의 결합

Director만 똑똑하고 플레이어 선택이 없으면 “지켜보는 AI”에 그칩니다.

| 플레이어 선택 | Director/시스템 반응 |
|---------------|----------------------|
| 카드 Skip | 빌드 희석 방지 (Spire) |
| Safe 루트 | RELAX · 회복 · 낮은 위험 |
| Elite 루트 | Rare 확정 · 고위험 |
| 세트 완성 | Q 스킬 정체성 변화 |
| No-Hit 클리어 | 다음 방 Peak 강화 후보 |

## 8. 검증 방법

| 방법 | 내용 |
|------|------|
| `tools/playtest.mjs` | Playwright 봇이 Safe/Elite 풀런 수행, 승패·에러 수집 |
| `?demo=1` | 자동 플레이로 시연 영상 생성 |
| UI 검증 | Why / Phase / Report가 한 화면에 읽히는지 |

버그 사례(이미 수정): hitstop 미감쇠로 정지, 적 0명 리스폰으로 클리어 불가, 전투 중 벽 교체로 끼임 등.  
Verify 단계에서 AI 에이전트와 함께 재현·수정했습니다.

## 9. 본선 확장 스펙 (초안)

사전과제 테이블을 문서 템플릿으로 고정했기 때문에, 본선은 “새로 발명”이 아니라 **확장**입니다.

### 9-1. 에이전트 설계서에 옮길 항목
- Observe 스키마 (필드, 정규화, 윈도우)
- Action ontology (이름, 비용, 선행조건, 부작용)
- Budget 경제 (수입/지출/상한)
- Safety: PEAK_FADE 금지 집합

### 9-2. 디렉팅 명세서에 옮길 항목
- Phase 그래프와 최소 체류 시간
- Why 문장 템플릿 카탈로그
- 스타일별 스폰 프로파일
- Eval 지표: 개입/분, Phase dwell, 데스 구간 히트맵

### 9-3. 선택적 LLM 확장 (본선)
규칙 Director를 유지한 채, Explain 단계만 LLM으로 Why 문장 다듬기 / 보스 연출 카피를 생성하는 하이브리드를 검토할 수 있습니다.  
Decide/Act의 안전 규칙은 코드에 고정하는 방향을 권장합니다.

---

## 10. 결론

Director Loop의 AI 활용은 두 층입니다.

1. **제작층:** Cursor 에이전트로 Observe–Decide–Rebuild–Verify를 빠르게 회전  
2. **런타임층:** 설명 가능한 Director가 Phase·Memory·Budget·Why로 연출  

사전과제에서 이미 UI·코드·플레이테스트로 검증했고, 본선 문서의 뼈대로 바로 쓸 수 있습니다.
